# リリース検証手順

## 目的

[`harness/evidence.json`](../harness/evidence.json)の未確認値を、観測した結果だけで更新する。失敗は未確認に戻さず、経路、端末、操作、期待値、実測を残してP0/P1として扱う。個人名、メールアドレス、端末のローカルIPは記録しない。

## 事前条件

- `npm run loop:check`が成功する。
- `npm run pack`で生成した`no-service.ehpk`を使用する。
- G2、R1、Even Appのバージョンと検証日を反復ログへ記録する。
- G2を十分に充電し、電話の省電力設定を通常利用時と同じにする。
- 各経路はスマホ側の「最初から」で進行状態を消してから開始する。

## 実機全27経路

各3桁は、`choice_year`、`choice_safety`、`choice_final`で選ぶ0始まりの候補indexである。各行で次を確認する。

- 20ノードで終端へ到達する。
- 選択直後のメールが選択内容へ固有に反応する。
- 通り、人物、献花、17台の回収端末という4添付を判別できる。
- 3桁目が0なら読者保存、1なら予測欠損、2なら次の宛先へ到達する。
- ENDの決定入力では表示を保持し、戻る操作で終了確認が表示される。

## 入力・復元・耐久

| ID | 手順 | 合格条件 | 結果 |
| --- | --- | --- | --- |
| HW-INPUT-G2 | G2で上下、決定を各3回行う | 1操作につき1移動または1確定。欠落、二重入力、逆方向なし | ☐ |
| HW-INPUT-R1 | R1で同じ操作を行う | G2と同じノード列・選択結果になる | ☐ |
| HW-LOCK | 添付ノードで電話をロックし、G2から決定する | 電話を開かず次のメールへ進む | ☐ |
| HW-IDLE | 選択画面で2分間操作せず、その後上下・決定する | 選択が1段だけ動き、選んだ返信へ進む | ☐ |
| HW-RESTART | 添付ノードでEven Appを終了し、再起動する | `attachment_portrait`を復元し画像を再送する | ☐ |
| HW-RETRY | `?evidenceCase=hardware-retry&failAttachmentOnce=1`で検証URLを開く | エラー表示後、決定で画像が出て次メールへ進める | ☐ |

成功した項目だけ、順に`hardware.g2Input`、`r1Input`、`lockedPhone`、`idleTwoMinutes`、`attachmentRetry`へ反映する。HW-RESTARTは反復ログへ画像とともに残す。

## 5人ユーザーテスト

参加者はP01〜P05の匿名IDだけで記録する。操作説明は「上下で選択、決定で進む、いつでも終了できる」だけとし、物語設定は事前説明しない。

### 観測

1. 開始から「2008年との時間差」と「返信が必要」を本人の言葉で説明するまでを計測する。
2. 終了後に「続きを読みたい」を1〜5で回答してもらう。
3. 次の6項目を1〜5で回答してもらう。

| 項目 | 質問 |
| --- | --- |
| Hook | 60秒以内に異常と目的を理解できたか |
| Character Voice | 名前を隠してもミナの文体を識別できるか |
| Temporal Mystery | 続きを知りたい具体的な疑問が残ったか |
| Choice Tension | 少なくとも1回、返信を迷ったか |
| Ending Pull | 次話を自発的に読みたいか |
| Device Fit | スマホではなくG2である意味を感じたか |

`userTest`には人数と成功数を記録する。`narrativeReview`には6項目それぞれの5人平均を小数1桁で記録する。参加者4人以上が60秒以内、4人以上が続きを4以上、6平均すべてが4.0以上の場合だけ該当ゲートを合格とする。

## 最終判定

1. P0/P1不具合が0件であることを確認する。
2. `npm run loop:check:release`が成功する。
3. 審査用60秒デモを3回連続で実行し、入力欠落、黒画面、画像失敗がないことを記録する。
4. `npm run pack`を再実行し、検証したソースと配布物を一致させる。
