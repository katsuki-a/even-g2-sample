# ループエンジニアリング

## 目的

各ループで、仮説を1つ選び、最小の変更を行い、自動評価と人手証拠の両方で完成形へ近づいたことを確認する。大規模な書き換えを「進捗」とみなさない。

## 標準ループ

```text
1. 現在段階と最低点を確認
2. 最も低い適応度またはハードゲートを1つ選ぶ
3. 失敗を再現するテスト・証拠を先に追加
4. 最小の実装または台詞変更を行う
5. npm run loop:check を実行
6. シミュレータまたは実機で人間が確認
7. 前後スコアと判断をiteration logへ記録
8. 改善なら保持、悪化なら原因を除去
```

## コマンド

```bash
npm test
npm run fitness
npm run loop:check
npm run narrative:prepare
npm run narrative:verify
npm run loop:check:narrative

# 次段階を先取りして不足を見る
npm run fitness:implementation
npm run fitness:release
```

`harness/config.json`の`activePhase`が通常の`fitness`と`loop:check`の段階を決める。段階昇格は、現段階で90点以上かつ次段階のハードゲートが列挙できた時だけ行う。

## 段階昇格

### concept → implementation

- conceptスコア90以上
- ストーリーの全経路がレビュー済み
- P0要件と非目標に未決定項目がない
- 実装モジュールの責務が合意済み

### implementation → release

- implementationスコア90以上
- 自動テストとビルドが成功
- シミュレータで全経路を完走
- P0不具合0件
- 実機テスト手順が確定

### release → complete

- releaseスコア85以上
- すべてのrelease evidenceが確認済み
- 5人テストの定量条件を満たす
- 審査用60秒デモを失敗せず3回連続で実行

## 作業単位

1ループは次のいずれか1種類に限定する。

- `story`: 台詞、分岐、情報開示
- `engine`: 状態遷移、保存、テンプレート
- `renderer`: G2レイアウト、画像、差分更新
- `input`: G2/R1操作、イベント正規化
- `resilience`: 再接続、再起動、失敗復旧
- `polish`: タイミング、点滅、グリッチ、添付画質

複数種類へまたがる場合は、検証可能な小さいコミットへ分割する。

## 反復ログ

各ループは[`docs/iterations/TEMPLATE.md`](./iterations/TEMPLATE.md)をコピーして記録する。

最低限、以下を残す。

- 仮説
- 変更前スコア
- 変更内容
- 自動評価結果
- シミュレータまたは実機の観察
- 変更後スコア
- 採用・破棄の判断
- 次に残った最大リスク

## 物語のループ

台詞変更では、文字数だけを削らない。

1. そのメールの唯一の役割を1文で言う。
2. 役割に不要な説明を削る。
3. ミナ以外でも言える文を人物固有の観察へ置き換える。
4. 選択直後の返信が選択を認識しているか確認する。
5. 全経路を読み、情報開示順を評価する。
6. `npm run narrative:prepare`で現在の全完走経路を固定する。
7. 5つの独立sub-agentへ担当パケットだけを渡し、他人格の点数を見せずに採点する。
8. 生レビューを`harness/narrative/reviews/`へ保存し、`npm run loop:check:narrative`でNarrative品質、通常fitness、テスト、ビルドを一括確認する。
9. iteration logへinput digest、人格別点、面白さ、非凡庸性、最低経路を記録する。

台詞または遷移を変えたら既存レビューは失効する。点数を見た後に閾値を下げず、最低軸を次ループの単一仮説として扱う。sub-agentは作者資料や他人格の評価を読まないブラインド入力とし、実ユーザー評価は別途残す。

## 実装のループ

1. ドメイン層の失敗テストを書く。
2. Fake Clock、Fake Storage、Fake Rendererで修正する。
3. 実SDK Adapterへ接続する。
4. シミュレータで同じ操作列を再生する。
5. 実機固有の差分だけをAdapterへ閉じ込める。

## 停止条件

次の場合は追加機能を止める。

- 95点以上で、追加変更が人手評価を改善しない。
- 新機能がP0要件を不安定にする。
- 60秒デモに新しい説明が必要になる。
- 権限、ネットワーク、自由入力を増やさないと成立しない。
